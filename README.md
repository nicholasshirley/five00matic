# five00matic

Error tickets in the repo instead of Sentry's inbox. The sentry-ruby SDK
assembles each error event as it always has; a `before_send` hook hands it
to this gem, which turns each unique error into a well-formatted GitHub
issue, posted by a GitHub App of its own, with throttled recurrence
notices. Sentry's servers stay in the loop or not, per mode. The gem
depends on nothing beyond the Ruby stdlib; delivery from a job runs on
the app's own ActiveRecord and ActiveJob.

Built against the payload shape of sentry-ruby 5.10 and checked against
events generated by 6.7 and 7.0. Ruby 3.2 or newer; CI runs the suite on
3.2, 3.4 and 4.0. Delivery from a job needs Rails 7.1 or newer and is
tested on 8.1.

## Layout

```
lib/five00matic.rb             entry point: tracker(config), before_send(...)
lib/five00matic/version.rb     the gem version
lib/five00matic/config.rb      env-driven configuration
lib/five00matic/credentials.rb a token, or a GitHub App minting its own
lib/five00matic/event.rb       the SDK payload: fingerprint, title, sections
lib/five00matic/group.rb       one fingerprint: counts, its issue, notice anchors
lib/five00matic/store.rb       the groups, persisted (JSON file, file-locked)
lib/five00matic/database_store.rb  the groups as rows of the app's database, with delivery claims
lib/five00matic/group_record.rb    the ActiveRecord model of a group's row
lib/five00matic/ticket.rb      GitHub-issue markdown rendering
lib/five00matic/notice.rb      recurrence-notice comment rendering
lib/five00matic/delivery_error.rb  delivery failures (DeliveryError, IssueGone)
lib/five00matic/github.rb      thin GitHub REST client
lib/five00matic/outbox.rb      dry-run stand-in: tickets as markdown files
lib/five00matic/tracker.rb     record an occurrence, deliver what GitHub is owed
lib/five00matic/queued_tracker.rb  record on the hook's thread, deliver from a job
lib/five00matic/delivery_job.rb    the ActiveJob that delivers, with retries
lib/five00matic/scrubber.rb    cookies, auth and filtered params out of the event
lib/five00matic/hook.rb        the before_send callable: scrub, track, decide
lib/five00matic/app.rb         the RACK app (POST /events, GET /health, /issues)
lib/five00matic/engine.rb      bin/rails five00matic:install:migrations
db/migrate/                    the five00matic_groups table
bin/serve.rb                   zero-dependency standalone server (stdlib TCPServer)
config.ru                      RACK entry (puma/rackup) for a standalone receiver, mounted at /sentry
scripts/make_sample_event.rb   generates a real event using the installed SDK
test/                          minitest suite
sample/                        generated sample payload (gitignored)
data/                          groups.json + outbox/ (gitignored)
```

## Wiring a Rails app

Gemfile:

```ruby
gem "five00matic", github: "nicholasshirley/five00matic"
```

The table the groups live in, copied into the app's migrations:

```sh
bin/rails five00matic:install:migrations
bin/rails db:migrate
```

After an update, running the first command again copies only the
migrations the app does not have yet.

Credentials (`bin/rails credentials:edit`), from the GitHub App described
below:

```yaml
five00matic:
  app_id: 123456
  private_key: |
    -----BEGIN RSA PRIVATE KEY-----
    ...
    -----END RSA PRIVATE KEY-----
```

The Sentry initializer:

```ruby
Sentry.init do |config|
  config.dsn = ENV.fetch("SENTRY_DSN") # the SDK sends nothing, hook included, without a DSN

  config.before_send = Five00Matic.before_send(
    repo: "you/your-app",
    app_id: Rails.application.credentials.dig(:five00matic, :app_id),
    private_key: Rails.application.credentials.dig(:five00matic, :private_key),
    delivery: :active_job,
    data_dir: Rails.root.join("tmp", "five00matic"), # the dry run's outbox
    filter: ActiveSupport::ParameterFilter.new(Rails.application.config.filter_parameters),
    mode: :shadow,
    logger: Rails.logger
  )
end
```

For each error event, on the thread the SDK sends from, the hook scrubs
the event and counts it in `five00matic_groups`. When GitHub is owed
something, the issue or a recurrence notice, it enqueues
`Five00Matic::DeliveryJob` on the app's queue, so neither a request nor
a job waits on GitHub. The job claims the error's row, so two deliveries
of one error cannot both open its issue, and delivers what the row says
is owed. A failed delivery is retried with growing waits for about four
hours; after that the failure stays on the row, and the error's next
occurrence queues another delivery. Then:

- `mode: :shadow` returns the event, so Sentry receives everything it did
  before and GitHub gets tickets besides. Compare the two for a while.
- `mode: :replace` returns nil once the event is counted, so Sentry never
  sees it. An event the hook could not take (its database unreachable,
  say) is logged and still goes to Sentry; a GitHub delivery that fails
  is not that case: it is retried as above, and the event is dropped
  from Sentry as owned.

Notes:

- While the database cannot be reached, the hook records nothing: the
  error is logged and reaches Sentry only, in either mode. Keep the DSN,
  and Sentry, until
  [#7](https://github.com/nicholasshirley/five00matic/issues/7) adds a
  fallback.
- A failure of `DeliveryJob` itself (a bug, or the database lost
  mid-delivery) goes to Sentry untracked, recognised by the job class
  sentry-rails reports it with: tracking it would queue another delivery,
  which could fail the same way.
- The job runs on whatever adapter the app's ActiveJob uses. The claim is
  the gem's own, in the table, not the adapter's.
- Without `app_id` and `private_key` (or a `token:`), tickets are written
  to `data_dir/outbox` as markdown files: a dry run for development.
- `send_default_pii` can stay on. The scrubber drops cookies, the
  Authorization header and the Rack env beyond the SDK's default
  `REMOTE_ADDR`, `SERVER_NAME` and `SERVER_PORT` whatever the settings,
  and runs the app's `filter_parameters` over the request body, the query
  string, breadcrumb data, user, tags, extra and contexts. The SDK never
  applies that filter to the request body: through sentry-ruby 6 the body
  goes out as submitted, and 7 masks only top-level keys from its own fixed
  list, so a failed login would otherwise file the password. Sentry
  receives the event unscrubbed, as before.
- The hook never raises into the SDK.

### Delivering inline

`delivery: :inline`, the default, keeps the groups in a JSON file under
`data_dir` instead of the database, and delivers on the hook's thread:

- `data_dir` must then survive deploys and be shared by every process of
  the app on its host: Puma's workers and the Solid Queue workers its
  plugin forks each run the hook. Under `storage/` on the persistent
  volume is the usual place. Hosts cannot share it (see State below).
- The hook answers only as fast as GitHub does. The SDK queues 30 events
  for its worker and drops beyond that, and sentry-rails sends a job's
  errors from the job's own thread, so a GitHub that stalls holds the job
  for up to the gem's HTTP timeouts.
- A failed delivery is retried on the error's next occurrence only.

### The GitHub App

Under the account that owns the repos: Settings, Developer settings,
GitHub Apps, New GitHub App. Repository permissions: Issues, read and
write; Metadata is added read-only by itself. Nothing else, no webhook.
Generate a private key, then install the app on the account for the repos
that should receive tickets. Issues appear as `<name>[bot]`. The gem looks
up the installation itself and expects exactly one.

A personal access token with the same scope works instead, as `token:`.

## Running the standalone receiver

For an app that cannot load the gem, the same pipeline runs as an HTTP
receiver. The receiver needs no gems; the tests do, for the database
store and delivery job:

```sh
# tests
bundle install
bundle exec ruby -Ilib -Itest -e 'Dir["test/*_test.rb"].each { |f| require File.expand_path(f) }'

# dry-run server (no credentials): tickets land in data/outbox/ as .md files
TICKET_NOTICE_INTERVAL=2 ruby bin/serve.rb      # port 9292, 127.0.0.1

# real delivery as a GitHub App (Issues: read and write), or with a token
TICKET_REPO=you/your-repo TICKET_APP_ID=123456 TICKET_APP_KEY_FILE=app.pem ruby bin/serve.rb
TICKET_REPO=you/your-repo TICKET_TOKEN=ghp_xxx ruby bin/serve.rb

# an error filed only to the outbox has no GitHub issue yet; its next
# occurrence after the switch opens one. Changing TICKET_REPO works the same
# way: issues stay with the repo they were opened in.
```

`lib/five00matic/config.rb` lists every `TICKET_*` variable. `bin/serve.rb`
is for local use; for anything else run `config.ru` behind a real app
server, which mounts the app at `/sentry`.

Generate the demo payload (runs under the RVM 3.2.0 where the 5.10 SDK lives):

```sh
GEM_HOME=$HOME/.rvm/gems/ruby-3.2.0 \
GEM_PATH=$HOME/.rvm/gems/ruby-3.2.0:$HOME/.rvm/rubies/ruby-3.2.0/lib/ruby/gems/3.2.0 \
$HOME/.rvm/rubies/ruby-3.2.0/bin/ruby scripts/make_sample_event.rb

curl -s -X POST --data-binary @sample/event.json http://127.0.0.1:9292/events
```

### Posting to it from an app

In the app's Sentry init, intercept in `before_send` and deliver to the
receiver:

```ruby
TICKET_URI = URI(ENV.fetch("TICKET_URL", "http://127.0.0.1:9292/events"))

Sentry.init do |config|
  config.dsn = ENV.fetch("SENTRY_DSN") # keep a valid DSN; the SDK needs it to enable sending

  config.before_send = lambda do |event, _hint|
    response = Net::HTTP.start(TICKET_URI.host, TICKET_URI.port,
                               use_ssl: TICKET_URI.scheme == "https", open_timeout: 2) do |http|
      http.post(TICKET_URI.path, event.to_json_compatible.to_json, "Content-Type" => "application/json")
    end
    # nil stops the event from going to Sentry at all; only do that once the
    # receiver has taken it
    response.is_a?(Net::HTTPSuccess) ? nil : event
  rescue StandardError
    event # receiver unreachable: fall back to Sentry rather than losing the event
  end
end
```

Notes:

- The default `TICKET_URL` is `bin/serve.rb`'s address. `config.ru` mounts
  the app at `/sentry`, so for a receiver run from it, point `TICKET_URL` at
  `/sentry/events`.
- Returning `event` instead of `nil` double-sends (Sentry + receiver).
- If the POST raises (receiver down) or is refused (any non-2xx), returning
  `nil` would lose the event: Sentry never sees it and neither does GitHub.
  The hook above returns `event` in both cases so Sentry takes it as a
  fallback; drop that if you would rather lose the event than double-report.
- The receiver delivers to GitHub inline, so it answers only as fast as
  GitHub does; the SDK worker waits for it (Net::HTTP's default read timeout
  is 60s). The short open timeout keeps an unreachable receiver from holding
  the worker that long.
- The receiver does not scrub: this hook sends the event as the SDK built
  it, cookies and all. Scrub in the lambda, or turn `send_default_pii` off.
- `before_send` is the only intake. Don't point `SENTRY_DSN` at the receiver:
  the SDK would post envelopes to `/api/<project>/envelope/`, which it does
  not serve.

## Behavior

- **Fingerprint** (dedup key): an explicit non-empty `event["fingerprint"]`
  wins; otherwise the raised exception's type + the file and function of
  each in-app stack frame (every frame, when the SDK marked none in-app).
  Line numbers, messages and tags are deliberately left out: they vary
  between occurrences of one bug (a deploy shifts lines; messages carry ids
  and, on Ruby 3.2, object addresses; tags carry request ids). The message
  is used only for an exception with no stack trace, or a message event.
- **Rejected with 400** (the HTTP receiver) or passed to Sentry untracked
  (the hook): a body that is not a JSON object, one holding invalid UTF-8
  or a non-finite number (the SDK can produce neither), and an event with
  neither an exception nor a message. Sections of an unexpected shape are
  otherwise read as empty rather than refused.
- **First occurrence** of a fingerprint: an issue is opened. With
  `delivery: :inline` and in the HTTP receiver, that is at once, with a
  count of 1. With `delivery: :active_job`, it is when the queued job
  runs, and the issue counts every occurrence recorded by then.
- **Recurrences**: count increments on every event, but a GitHub notification
  (comment) is only sent once per `TICKET_NOTICE_INTERVAL` (default 6h). The
  comment reports new-since-notice and total counts plus the latest event id.
- **Delivery failures** are recorded on the fingerprint and retried on the
  next occurrence (the count was already persisted, so no event is lost);
  the HTTP response still reports 200 because the sender has handed off
  ownership. With `delivery: :active_job` the job first retries on its
  own, for about four hours. A GitHub App token that cannot be minted is
  such a failure.
  If GitHub answers 404 for a recurrence comment (the tracked issue was
  deleted, or the repo was re-created), the dead issue is dropped and a
  replacement opened; should that fail too, the next occurrence opens one.
- **Ticket size**: GitHub rejects issue bodies over 65,536 characters, so
  rendered tickets are capped below that. The raw-payload section switches to
  compact JSON and is clipped first; only an event whose structured sections
  alone overflow gets those clipped too.
- **State**, with `delivery: :active_job`, is a row per fingerprint in
  `five00matic_groups`, counted under a row lock, so every process and
  host on the database counts against one set of groups. A delivery's
  claim on its row lapses after 10 minutes, so a worker that dies
  mid-delivery does not hold its error for long. A queued delivery
  carries the scrubbed event, so the queue's tables hold what the ticket
  will show until the adapter clears them.
- **State**, with `delivery: :inline` and in the HTTP receiver, is a
  single JSON file (`data/groups.json`), read and written under a file
  lock, so every process sharing the directory (a web server and the job
  workers it forked, say) counts against one set of groups; restarts and
  redeploys keep counts and throttle anchors. State and outbox files
  carry event content (user ids, request bodies) and are written
  owner-only (0600). Hosts cannot share a data directory: run one host,
  or one receiver that every host posts to.

## Known simplifications

- `delivery: :inline` and the HTTP receiver deliver inline, with no queue
  (fine at dormant-project scale).
- Delivery is at-least-once: if GitHub times out after creating an issue but
  before the response arrives, the retry opens a duplicate issue. Issue
  creation has no idempotency key.
- The JSON state file is single-host. Record-to-delivery is serialized
  per fingerprint across the processes of one host, so they will not
  double-open an issue; two hosts with their own data directories would.
- `bin/serve.rb` is a convenience, not a server: thread-per-connection, no
  read or header timeouts, no chunked-encoding or request-size limits. A
  slow client can hold a thread open; a hostile one can hold many. For
  anything but local use, run `config.ru` behind a real app server instead.
- Fingerprinting approximates Sentry's: two raises of one exception type in
  the same method share a ticket, and `{{ default }}` in an explicit
  fingerprint is taken literally rather than expanded.
- No authentication on the HTTP receiver endpoint itself; put it behind your
  normal internal-network/secret controls.
